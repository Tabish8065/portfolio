Real-time · Distributed

Real-time messaging pipeline

Problem. Messages, presence, and typing indicators had to reach every connected device the moment data changed, without clients polling.

What I did. I designed and maintain the path from database writes to live clients. Database change events feed a SignalR hub, which fans them out over WebSockets to the Flutter apps.

Result

Live delivery, presence, and typing across iOS, Android, and web.

Staff see new messages, who is online and who is typing the moment it happens, on any device, without the apps repeatedly asking the server.

Design and patterns

  • Observer and publish/subscribe over database change events instead of request polling.
  • Server-authoritative access. Removed members keep the history they were allowed to see, but receive no new live events.
  • Membership changes go out as metadata events. The visible timeline is persisted as messages, so reconnecting clients rebuild it from history.
  • On the client, one realtime session is owned at the composition root and injected, not constructed by each screen.
  • Observer
  • Pub/Sub
  • Fan-out
  • Server-authoritative state
  • WebSockets

Attachment contract redesign

Problem. Clients fetched appointment and invoice data again every time an attachment was rendered.

What I did. I redesigned the contract so that data travels inside the message payload. It also covers group bookings, multi-service appointments, and two guest-profile versions.

Result

Redundant backend calls removed and client load time down 70%.

Appointment and invoice attachments open 70% faster because their data arrives with the message, and older app versions keep working during rollout.

Design and patterns

  • Data is enriched once at write time and read many times, so render time no longer pays for it.
  • Backward compatible, so older mobile builds keep working during rollout.
  • A versioned guest-profile shape served from the same contract.
  • Write-time denormalization
  • Contract versioning
  • Backward compatibility

Product · Plan tiers

Features that sell the paid plan

Most of these ship behind plan entitlements. They are the capabilities that move customers to a higher tier, and I built them end to end: API, data model, real-time events, and Flutter UI.

Cross-center messaging and search

Staff at multi-location businesses can message and search across every location they are assigned to, from one interface.

How it works

  • Each user's reach is derived from their role-to-location assignments. Nobody gets org-wide reach by default.
  • One location-agnostic direct room per user pair, with location labels added per message.
  • Access is validated when a message is sent, not only when the room is created.
  • Backend query layer plus the Flutter search experience.

Tier-aware message lifecycle

The server decides retention from the customer's plan: time-boxed on free, kept on paid, and recoverable after an upgrade.

How it works

  • Plan stored with location settings and read atomically, with no joins.
  • Cleanup excludes the paid minority with a denylist, so new locations default safely to free.
  • Paid IDs are re-read every batch, so a customer who upgrades mid-run is never purged.
  • Recovery uses cursor pagination, constant cost per page instead of offset skips.

Group membership administration

Admins add, remove, promote, and dismiss members. Leaving and re-joining behave predictably for history and live access.

How it works

  • Invariant: the last active admin cannot leave until they promote someone.
  • Atomic document updates, plus a per-room Redis lock that fails open so it never blocks writes.
  • Re-adding a member never shrinks history they were previously granted.
  • Real-time membership events keep every device consistent.

Shared files hub

Every image, document, and business attachment in a conversation, browsable in one place for 1:1 and group chats.

How it works

  • One endpoint per visible section, fetched only when the plan flag is on and the tab is open.
  • A compound multikey index plus keyset pagination. There is no separate hub collection to keep in sync.
  • Obeys the same history-visibility rules as the chat itself.

Streaming storage library

Problem. Large file exports and uploads could not be buffered in memory, and every team was solving storage separately.

What I did. I generalized the export storage work into Zenoti's shared platform package, so any Zenoti service can use it. It is platform infrastructure, not a product feature.

Any Zenoti service can now export or upload large files without holding them in memory, instead of each team solving storage on its own.

Design and patterns

  • Block-staged streaming upload. Content is written as blocks and committed once, so a large file never sits whole in memory.
  • Gzip compression and image thumbnail generation in the same package.
  • A storage provider abstraction, so callers depend on an interface and not a cloud SDK.

Architecture

Composable authorization policy pipeline

Problem. Plan, role, location-scope, membership, and masking checks were scattered across services, and each new action meant touching several of them.

What I did. I designed one pipeline. The request model passes through small, independently testable policies and returns a decision with a reason and obligations.

One place now decides what each person can do based on plan, role, location and membership, so adding a new action no longer means changing several services.

Design and patterns

  • Policies: plan entitlement, role permission, role scope, room membership, cross-location access, attachment location. Contact masking is an obligation, not an allow/deny.
  • Lazy evaluation, so expensive remote and database lookups run only when the action needs them.
  • The same evaluator powers both the UI capability response and backend enforcement, so the two cannot drift.
  • A new action is an enum value plus one catalog row. A new policy class is needed only for a new kind of rule. Existing 401/403 contracts are preserved.

Distributed coordination

Distributed coordination and reliability

Pod-aware onboarding queue

Onboarding work runs on the regional deployment that owns the customer. No deployment steals another's queue.

  • Each deployment claims its own work first, in FIFO order per organization.
  • Owner-fenced locks, taken only when writes begin.
  • Fail-closed routing: if ownership lookup fails, the work is not enqueued in the wrong place.
  • A black-box concurrency harness to prove the claims under contention.

Distributed rate limiting

One per-client request limit enforced identically across every API pod.

allowed 0 · limited 0 · illustration
  • A Redis-backed token bucket evaluated in a single atomic Lua script, never read-compute-write.
  • Evaluated against GCRA. Both are smooth, with no fixed-window burst at boundaries.
  • Limiter state is visible on my observability dashboard.

Analytics and UI reliability

Fixed a production analytics defect where the organization ID was emitted as 0 for enabled organizations, which had been silently corrupting downstream tracking. Resolved and hardened 15+ cross-platform UI issues: themes, timestamps, role filters, permissions, and rendering.

  • Traced the bad identifier from the emitted event back to the code path, then corrected attribution at the source.
  • Negative caching for organization settings, so repeated lookups for missing records stop hitting the database.

Flutter architecture

Layered, incremental client architecture

What I did. I defined an architecture standard for the Flutter client and migrated it screen by screen, with no rewrite and no delivery freeze. Public events, states, APIs, and UX stayed unchanged at every step.

  1. Composition rootowns long-lived services
  2. Screen + UI policyimmutable snapshots
  3. BLoC / Cubitowns data loading
  4. Repositoryrequest cancellation
  5. API · Realtime sessioninjected
Result

Smaller, testable units, with the test suite green at every layer.

The app was restructured screen by screen with no rewrite and no delivery freeze, and nothing changed for users along the way.

Design and patterns

  • A composition root owns long-lived services like the realtime session. Screens receive dependencies and never construct them.
  • Oversized BLoCs split into focused collaborators, with public events and states unchanged.
  • Typed routes and route arguments.
  • Auth state read once at composition and injected as immutable UI policy snapshots, so widgets never reach into global services.
  • Repository layer with request cancellation. Cubits own data loading.

  • Immutable snapshots
